# OPS-FABRIC ALERT FLOOD — ROOT CAUSE + FIX

> 2026-09-22 · hermes-edge-bridge · F13 directive context: "fix all the gaps and seal it. No over engineering. REALITY > EVERYTHING"
> Symptom: `[FORGE] STATE=HOLD SOURCE=arifos.floor.breach ... TRACE_ID=trc-...` repeating in the AAA group for ~45 hours.

## What was actually happening

Not one breach. **One condition, 111 emissions, 111 Telegram alerts.**

Chain:
1. `surface-guard.service` (MCP drift watchdog) intermittently reads A-FORGE-MCP's tool surface from a
   **cold transport** and sees all 122 tools "removed". It publishes `888_HOLD` to NATS subject
   `arifos.floor.breach`.
2. `aaa-ops-bus-worker.service` (durable JetStream consumer) receives it and calls
   `aaa_ops_envelope.emit(...)` with a **fixed** action string → idempotency_key
   `da1dcfdc9f321a68` — the same 16-hex fingerprint every single time.
3. `emit()` has an anti-storm dedup. It computed the fingerprint correctly and then
   **never used it correctly**.

## The bug (one line)

`/root/scripts/aaa_ops_envelope.py:63`

```python
# BEFORE — measures elapsed time since the condition was FIRST SEEN
fresh = (now - first_ts) > DEDUP_WINDOW_S or last_notify == 0
```

`first_ts` is written once and never updated. So once any condition lives longer than the 6h window,
`(now - first_ts) > 6h` is **permanently true** → every emission notifies → flood.

```python
# AFTER — measures elapsed time since the LAST NOTIFY (what the docstring always said)
fresh = last_notify == 0 or (now - last_notify) > DEDUP_WINDOW_S
```

The function's own docstring described the correct contract:
*"the FIRST occurrence of a condition always notifies. Repeats inside the window are recorded with
suppressed=true and notify=False. After the window lapses the condition re-notifies once."*
The code implemented the opposite of its own spec.

## Second defect: the worker was running 45-hour-stale code

| worker process started | Mon 2026-09-21 **01:53:17** |

always writes. The patch had never executed once.

## What was NOT changed (deliberately)

- **`surface-guard` alert sensitivity.** The guard alerts on the first `HOLD` reading
  (`onDrift`: `if (report.status === 'HOLD' || consecutiveDrifts >= 2)`), and its confirmation probe
  discards the transient on the *following* cycle. Reordering that changes *what HOLD means* on a
  governance watchdog — a direction-of-record change, not quiet engineering. Same reasoning the
  2026-09-20 baseline-persistence receipt applied to restart-amnesty. Left for an F13 binary.
- **The A-FORGE-MCP cold/warm transport race** that produces the transient — root cause already
  documented 2026-09-20 (`surface-guard-oscillation-finding.json`, `baseline-persistence.json`).
  Still open. Not a one-line fix.
- Nothing else in `aaa_ops_envelope.py`; no schema change; no Telegram format change.

## Open findings (for F13, not auto-applied)

- **F-1 · guard alerts before it confirms.** First read → alert; confirmation → discard one cycle
  later. Bounded now by the dedup, but the alert itself is still a false positive.
- **F-2 · stale-worker class.** Any long-running process that imports a patched module keeps the old
  code forever. The 2-minute race here is the general case: *patch, then restart, or the patch is a
  no-op.* No mechanism currently enforces that ordering.
- **F-3 · the underlying flap.** A-FORGE-MCP cold transport reports a different tool surface than
  warm. Root cause unmapped since 2026-09-20; history was purged in the 38,283-file cleanup.
