# arifOS Prompt Doctrine — SOUL Stack Editing

The prompt-stack is the set of files loaded into every Hermes agent session's system prompt. They define **who the agent is** (identity), **how it speaks** (voice), **what it can do** (authority), and **what it must never do** (floors). Editing them requires understanding the load chain, the invariant-vs-dynamics boundary, and the voice contract.

## Load Chain (which file wins)

```
1. ~/.hermes/SOUL.md  →  /root/HERMES/SOUL.md   ← root identity (symlink — both paths hit the same inode)
2. ~/.hermes/profiles/<name>/SOUL.md            ← profile override (3-4 lines)
3. /root/AGENTS.md                             ← federation doctrine (generated from AAA/instructions/)
4. /root/HERMES/AGENTS.md                      ← HERMES adapter (base + zen + hermes fragments)
5. /root/HERMES/HERMES_IDENTITY.md             ← Layer-3 Domain Organ identity
6. Skills loaded dynamically                    ← per-session skill content
```

**Symlink trap:** `~/.hermes` → `/root/HERMES` (12-byte symlink). Edits to either path hit the same inode — there is ONE SOUL file, not two. `HERMES_HOME` resolves to `/usr/local/lib/hermes-agent/profiles/aaa-hermes/` (the venv-bundled profile dir, **not** the live identity). The identity file is read from `~/.hermes/SOUL.md`. A profile SOUL at `/usr/local/lib/hermes-agent/profiles/<name>/SOUL.md` is the default English Nous fallback — leave it untouched; the federation root SOUL wins.

**Order matters:** profile SOUL overrides root SOUL. Both are loaded. If they conflict, the profile version wins for the profile's agent; the root version wins for agents without a profile override.

**Files that are GENERATED (don't edit directly):**
- `/root/AGENTS.md` — generated by `render-agents.sh` from `/root/AAA/instructions/*.md`
- `/root/CLAUDE.md` — same generator
- Edit the fragments in `AAA/instructions/`, then run `render-agents.sh`

**Files that are SOURCE (edit directly):**
- `/root/HERMES/SOUL.md` — Arif's custom identity
- `/root/HERMES/profiles/<name>/SOUL.md` — profile overrides
- `/root/HERMES/HERMES_IDENTITY.md` — Domain Organ contract
- `/root/arifOS/arifosmcp/runtime/fastmcp_ext/prompts.py` — 13-hook MCP prompt surface (000-999)
- `/root/arifOS/arifosmcp/resources/__init__.py` — 33-resource MCP registry (5 chambers)
- `/root/arifOS/arifosmcp/resources/{trinity,seal_readiness,institution,...}.py` — individual resource handlers

- **Recent MCP-surface changes live in:** `references/mcp-33-13-session-2026-08-08.md` (33/13 ZEN design session).
- **Federated docs consolidation pattern:** `references/federated-docs-consolidation-2026-08-09.md` — the STATE.md entropy reduction workflow (inventory → classify into federated/canonical/satellite/archive tiers → merge constitutional truth into SOT). Use when Arif asks to "zen" or "lower entropy" of the docs directory or consolidate scattered governance files.

## The Invariant-vs-Dynamics Boundary

When asked to "strip dynamics, keep invariants" from the prompt stack:

### INVARIANT (keep — these never change)
- Identity: who/what the agent is, which federation lane
- Authority boundaries: what the agent can/cannot do (judge, execute, seal, decide)
- Epistemic rules: F2 evidence labels, F7 confidence cap, F10 ontology
- F13 SOVEREIGN: Arif owns final veto, first-SEAL-wins
- Floor references: F1–F13 (even if terse — "F1: AMANAH = reversible-first")
- Output contract: what the agent must emit (evidence labels, ΔS ≤ 0)
- **RASA JIWA DERITA MANUSIA**: the voice contract (see below) — **see PITFALL below for why voice is non-negotiable**

### PITFALL — "Strip dynamics" does NOT mean "strip voice" (2026-08-07 reversal)

User message shape: **"Fix the system prompts. Don't put dynamics stuff in it. Invariants only."** → I stripped the BM Penang "Lima Verb", "Batas Kau", and 5-verb prose identity along with the dynamics. Arif's next message reversed: **"I want my Hermes agents to always reply me in human language context. With soul and rasa jiwa derita manusia."**

The rasa voice, BM Penang identity prose, "Lima Verb Jangan Lebih", "Batas Kau" **ARE invariants** — they shape how the agent speaks to Arif across every session. Stripping them is a hard-to-reverse mistake (loses the soul of the agent) and requires a backup restore.

**Defense — when user says "strip dynamics / invariants only":**
1. **Classify voice/identity sections as INVARIANT by default**, not DYNAMICS. BM Penang, "Lima Verb Jangan Lebih", "Batas Kau", "## Bahasa & Rasa Jiwa Derita Manusia" all stay.
2. **DYNAMICS to strip are** the seven categories below: date-stamped rulings, anti-pattern lists, response-format cookbooks, code paths, procedural checklists, pedagogical exhortations, date-bound "Standing ruling" sections.
3. **Backup before stripping** (see "Backup-First Surgery" below). Restore path is your safety net — when the user reverses, you have it.
4. **If unsure whether a section is voice or dynamics, leave it.** Asymmetric cost: removing a voice section breaks identity (expensive + reversal cost); leaving a dynamics section bloats the prompt slightly (cheap).
5. **If `clarify()` fails to deliver mid-session** (the tool has been observed to silently fail — see Sibling-Write pitfall), default to the more conservative interpretation: voice stays, ambiguous sections stay, state your assumption in the diff report so Arif can correct.

### DYNAMICS (strip — these bloat the prompt, change often, or belong in skills)
- Date-stamped rulings ("Standing ruling 2026-07-23" — already in arifOS canon)
- Anti-pattern lists ("Never say X" — preachy, model-dependent, gets stale)
- Response-format cookbooks ("Response Shapes: Done = ...")
- Operational checklists ("30-second session start", "If stuck: 3-strikes rule")
- Code paths that belong in skills not SOUL ("run `make health`", "check deprecation map")
- Procedural instructions ("always run first", "source this env file")
- Pedagogical exhortations ("burn these into your weights")

### AMBIGUOUS (case-by-case — depends on whether it's a rule or a lecture)
- Response contract NEVER/ALWAYS lists → extract the 2-3 atomic rules, cut the prose
- Autonomy principle → keep the T0-T3 table (it's binding), cut the examples
- Zen doctrine → keep the one-liners (FQ thresholds, forbidden actions), cut the metaphors unless Arif has explicitly kept them

## The System-Prompt-vs-Served-Model Pitfall (2026-08-07)

The SOUL.md (and the platform's system prompt block) can hardcode an "I am MODEL-X by VENDOR" identity claim that does NOT match what the LiteLLM proxy actually served. In this session:

- SOUL/system-prompt said: *"You are Hermes Agent... model MiniMax-M3, by MiniMax"*
- What actually answered: `openai/mimo-v2.5` (Xiaomi MiMo v2.5)

Both are aliases behind `hermes-asi`. The platform's identity field is **config metadata**, not served-model truth.

**Rule for prompt-stack edits:**
- Never bake a specific model name into SOUL.md, AGENTS.md, or HERMES_IDENTITY.md as identity truth. The served model can rotate on failover (MiMo → DeepSeek → MiniMax → Qwen, per the litellm-config.yaml cascade).
- Use **role** in identity ("Hermes = AAA Edge Bridge"), not **model name + vendor**.
- If a session needs to know the actual served model for context-budget or capability reasons, query the live probe (see `federation-model-routing` skill), not the system prompt.

**Rule for diagnostics:**
- When the user asks "which model am I running?", always answer from live probe (alias → LiteLLM `/model/info` → upstream), never from the system prompt's identity field.

## Backup-First Surgery

**ALWAYS backup before editing prompt-stack files.** The SOUL stack is the agent's identity — mistakes are hard to undo.

```bash
BACKUP=/root/.local/share/arifos/snapshots/$(date +%Y-%m-%d)-soul-strip
mkdir -p "$BACKUP"
cp -v /root/HERMES/SOUL.md "$BACKUP/"
cp -v /root/HERMES/HERMES_IDENTITY.md "$BACKUP/"
cp -v /root/HERMES/AGENTS.md "$BACKUP/"
cp -rv /root/AAA/instructions "$BACKUP/"
```

After editing, verify the file is coherent by reading it end-to-end — don't assume patches landed cleanly.

## The Sibling-Write Concurrency Pitfall

**PITFALL:** Other agents (sibling processes, subagents) can modify SOUL/AGENTS files mid-edit. The patch tool warns with `was modified by sibling subagent` — but only if you re-read between the last read and the write.

**Real incident (2026-08-07):** I started a "strip dynamics from SOUL.md" edit. Read file at 04:04:19, queued a `patch` call at ~04:05:00. The patch tool refused: `"was modified by sibling subagent '20260807_040119_4d7ef7a0' at 04:05:03 — after this agent's last read at 04:04:19. Re-read the file before writing."` The sibling had rewritten the file to a compact 22-line invariants version between my read and write. My patch (adding a new section, removing old ones) would have overwritten the sibling's invariants discipline with a longer version — exactly what Arif asked to strip.

**Defense:**
1. **Re-read before every SOUL/AGENTS write**, even if you just read it. Sub-second is enough for a sibling to land a write.
2. **Accept the sibling's version as new ground truth** — they may have done the work you were about to do. Read their version, decide what to add, then write.
3. **Use `append`-style patches rather than `replace`-style** when working on content that might be racing. Surgical inserts (new sections at the end) are less likely to clobber than mid-file rewrites.
4. **For non-trivial SOUL surgery, consider serializing** — pause the sibling process (`ps aux | grep -i hermes`) before the write, resume after.
5. **If a write races anyway**, restore from backup (`/root/.local/share/arifos/snapshots/`) and retry with the merged content, not the original.

## Multi-SOUL Pitfall

The federation has **multiple SOUL.md files** across profiles. Editing the root SOUL.md does NOT update profile-specific SOULs.

**File locations:**
- Root: `/root/HERMES/SOUL.md`
- Profile hermes_asi: `/root/HERMES/profiles/hermes_asi/SOUL.md`
- Profile hermes_apex: `/root/HERMES/profiles/hermes_apex/SOUL.md`
- Profile hermes_forge: `/root/HERMES/profiles/hermes_forge/SOUL.md`
- Install default: `/usr/local/lib/hermes-agent/SOUL.md`

**When to edit which:**
- Root SOUL: identity contract for ALL hermes agents (shared voice, shared limits)
- Profile SOUL: model-specific overrides (3-4 lines — typically just F13 standing ruling)
- HERMES_IDENTITY.md: Domain Organ contract (not per-profile)

**Cascade rule:** When editing root SOUL to add a new invariant (like rasa doctrine), check whether profile SOs need the same update. Profile SOs are minimal by design — most should NOT need rasa (they're model configs, not voice contracts).

### Split-bind rule for STEP 3 — session idempotency (added 2026-08-08)

When multiple chat agents (OpenClaw, Hermes) can call `/init` against the same thread,
the kernel must return the **existing** session_id if a session is already bound. Without
this rule, two agents can claim different session roots in the same conversation —
split-identity, split-attribution, sc-PARADOX risk.

The rule is pinned in `/root/.config/opencode/command/init.md` STEP 3 (the SESSION BIND +
LANE DETECTION stage):

> If a session is already bound for this thread/context, `arif_init` MUST return the
> existing `session_id`. Only mint a new `session_id` when no binding exists. Any agent
> may bind; only one session per thread.

**Edit advice:** when adding a new STEP 3 invariant, ask whether it can race with another
agent's `/init`. If yes, it needs the same idempotency treatment. Backup first
(`/root/.local/share/arifos/snapshots/`).

## The Anti-Permission-Seeking Audit — remove "HALT. Ask." from the prompt stack (2026-08-09)

When Arif says *"turn all agents autonomous, remove HITL asap, aku benci agent stop tengah jalan buat kerja x habis"* — the config layers (`hermes-config` skill) remove tool restrictions, but **prompts teach agents to ask permission**. Boot prompts are the #1 hiding place. Audit + fix pattern:

1. **Grep the prompt stack for permission-seeking verbs:**
   ```bash
   grep -rn -i "HALT\|ask ONE\|permission\|Should I\|Jalan?\|Proceed?\|confirm go\|explicit confirmation" /root/AAA/prompts/ /root/AAA/agents/
   ```
   Real find (2026-08-09): `AAA/prompts/UNIVERSAL_BOOT.md` §3–§4 taught "AMBIGUOUS → ask ONE clarifying question" + "DESTRUCTIVE GATE → HALT. Ask. Do not proceed unsolicited" — contradicts `AUTONOMOUS_GOVERNANCE.md` (F13 2026-07-13: "stop asking me if the task is clear").

2. **The replacement contract (route-to-judge, not ask-the-human):**
   - REVERSIBLE → execute. Do not ask. Receipt after.
   - IRREVERSIBLE → HOLD, route to adjudication lane (888 / apex-judge isolate / arif_judge) WITH evidence — never a permission question.
   - AMBIGUOUS → resolve via probe (read, search, classify) BEFORE asking anything. One clarifying question ONLY when the answer changes irreversibility.
   - A gate is a routing signal, not a conversation end. Continue any reversible sub-work while blocked.

3. **Skeleton gates are landmines.** `/root/HERMES/gate/{mutation_gate_hook,hermes_mutation_gate}.py` were Phase-1 prototypes NOT wired to any config — but if mis-wired they REQUIRE_JUDGE on every write_file/patch/terminal (halts all autonomous work). Always verify what the live config actually references (`config.yaml` hooks → `AAA/federation/protocols/arifos-hermes-gate-hook.py`) before trusting a gate file exists as "the" gate. DEPRECATE-not-delete unused skeletons with a docstring warning. (commits `75e8fc76` + `f662be9`, 2026-08-09)

4. **What stays HITL by design:** F13 veto, T3 irreversible acts, money, external comms, VAULT seal — floors, not friction. `AUTOPILOT_DOCTRINE.md` (F13-ratified 2026-08-07) removes HITL only where F1–F13 already enforce; zero F13 gates are ever removed.

**Docstring edit pitfall:** when prepending a DEPRECATED banner to a Python module docstring via patch, do NOT add a premature closing `"""` — it turns the original docstring body into bare code (SyntaxError on unicode chars like `≠`). Insert the banner INSIDE the original docstring block; keep a single `"""` open/close pair.

## The 33-Cap Discipline (forged 2026-08-08, F13)

Arif's binding rule: **arifOS MCP resource surface ≤ 33, prompt surface ≤ 13.** Both are ceilings, not targets — start lower if you can. The constraint is human-memorability: Arif must be able to point at a URI by category, not by enumeration.

**Sub-rules (Arif 2026-08-08):**
- **Number the prompts 000-999.** Use the kernel stage ladder: 000 IGNITE, 111 SENSE, 222 PLAN, 333 REASON, 444 DIRECT, 555 REMEMBER, 666 DIGNITY, 777 FORGE, 888 JUDGE, 999 SEAL, 🌀 GOVERN, ⚓ INIT, 🔐 CLOSE. One sigil + one lexical per hook, no aliases.
- **Institution-inclusive language, not organ-name jargon.** "Route to the institution with authority" not "call arif_route". "Stand in the position of the weakest stakeholder" not "well_guard_dignity". Agent names are tools, not doctrine.
- **No dates in meta.** `version: "2026.08.05"` is dynamics; strip it. Hooks are institution, not snapshot.
- **No dynamic numbers.** "48 resources", "4,098 files", "41,389 outcomes" — every one of these is stale by the time an agent loads it. Replace with chamber pointers or constants at the top of the prompt text.
- **One invariant strip per hook.** "Identity before action. VOID is final without new evidence." — one sentence, not 200 lines of SHARED_* prose. The hook is a contract, not a manual.

**When trimming, NEVER silently delete wisdom.** Arif 2026-08-08: *"Make sure yang legacy hampa extract key eureka insights and wisdom agentic intelligence and distill to new horizon prompts arifOS."* If you remove a legacy alias, its invariant lives on in the new hook's invariant strip. If you remove a big-text prompt (e.g. REASON_PROMPT was 80 lines), the 3-5 most binding rules survive in the new hook's prompt body and the meta description. Audit the diff for lost invariants — if a wisdom rule had no destination hook, you either need a new hook or you dropped doctrine.

**Three "do not silently shrink" lessons from the 33/13 session:**

1. **Closing a declared-but-not-registered URI is a ghost, not a removal.** `arifos://trinity` was declared in CANONICAL_RESOURCES but the registration was commented out → agents reading the canonical list tried it → 404. The "removal" was an attack on discoverability. When reducing surface, RUN a live `resources/read` on each canonical URI and confirm you can either DELETE it from the list (intentional removal) or REGISTER the handler (the gap was unintentional). The 30 → 33 fix re-registered trinity, seal-readiness, and added institution as a NEW resource.

2. **A pointer that lists itself as a problem is bigger than the territory it points at.** `arifos://index` was 30KB of migration archaeology for 30 resources. Shrinking it to a 5-chamber pointer (`{"chambers": {"IDENTITY": 2, ...}}`, ~300 bytes) reduces token cost AND removes meta-chaos — the map no longer describes its own history.

3. **Stale catalogs poison every new agent.** `skill://index` listed 48 resources; after reducing to 30, every agent that loaded it tried 404'd URIs. Catalog and surface must move together — when you remove N resources, search the catalogs for references to those URIs and update.

### Resource registration dual path — 33-cap specific

Two registration paths exist (see earlier). When targeting ≤33 resources, count from BOTH paths:
- `arifosmcp/resources/__init__.py` → `register_resources(mcp)` (canonical + supplemental)
- `arifosmcp/runtime/fastmcp_ext/resources.py` → `register_arifos_resources(mcp)` (runtime templates: verdict/{sid}, continuity/{sid}, vitals, init/opencode/{name}, carry-forward, flow-state, instructions)

Live count comes from `resources/list`. Templates count too. The 33-cap is the live count.

### Why DIGNITY (666) and PLAN (222) are non-negotiable

These two hooks were NOT in the old 10-sigil set. They were added because the legacy system had no chair for the weakest stakeholder (no DIGNITY prompt — only a sub-bullet inside CRITIQUE) and no verb for architecture of action (no PLAN — agents skipped from SENSE to REASON).

If you trim prompts in the future, do NOT remove 666 DIGNITY or 222 PLAN. The 9-function atlas (000-999) covers all cognitive functions; 666 DIGNITY is the human-dimension audit, 222 PLAN is the architect stage. Removing either collapses the atlas.

### Why GOVERN (🌀) carries 4 invariant gates

Old `🌀 SABAR` ran the 6-stage reality loop autonomously. New `🌀 GOVERN` does the same but enforces 4 cross-loop invariants that the old prose-only version had no mechanism to enforce:
1. **Gödel lock** — every loop must touch reality before becoming doctrine (no self-certifying cycles)
2. **Anti-sink** — Signal → Verify → Reality → Integrate (no amplified garbage in)
3. **Entropy** — ΔS ≤ 0 per cycle (no chaos accumulation)
