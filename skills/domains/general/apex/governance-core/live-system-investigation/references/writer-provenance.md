# Writer Provenance — determining who changed a file

For systems where multiple agents/sessions share a host. The failure mode is
answering "I cannot determine who" after looking only at your own session record.

Run the steps in order; stop as soon as one yields a positive identification.

## 1. Sweep ALL sessions by timestamp window (not session-scoped)

The single most common miss: querying your own session, finding nothing, and
concluding unknowability. Every session's messages are in the same store.

```bash
sqlite3 <state.db> "
SELECT datetime(timestamp,'unixepoch','+8 hours') AS t, session_id, substr(content,1,140)
FROM messages
WHERE timestamp BETWEEN strftime('%s','2026-01-01 10:00:00') AND strftime('%s','2026-01-01 10:10:00')
ORDER BY timestamp;"
```

If `timestamp` is unixepoch and the host is not UTC, convert with `localtime` or an
`'+8 hours'` modifier so it matches the timestamps you were given.

Identify who was active at all:
```bash
sqlite3 <state.db> "
SELECT session_id, COUNT(*) n,
       datetime(MIN(timestamp),'unixepoch','+8 hours') first,
       datetime(MAX(timestamp),'unixepoch','+8 hours') last
FROM messages
WHERE timestamp BETWEEN strftime('%s','<start>') AND strftime('%s','<end>')
GROUP BY session_id ORDER BY n DESC;"
```
More than one row in a narrow window means **concurrent writers exist** — treat every
subsequent observation as possibly invalidated mid-flight.

Search content for the artifact, not just the time:
```bash
sqlite3 <state.db> "SELECT session_id, substr(content,1,200) FROM messages
WHERE content LIKE '%<artifact-name>%' AND timestamp > strftime('%s','<start>');"
```
`state.db-wal` may hold uncommitted pages; a match in the `-wal` file (via grep) that
is absent from the table means a write in flight.

## 2. Backup files bracket the change

A `.bak` / `.last-good` next to the target narrows both the actor and the method:

```bash
ls -lt --time-style=full-iso <dir>/<target>*
```

- Backup naming that embeds an ISO timestamp (`x.bak-<tag>-YYYYMMDDTHHMMSS`) is
generated by a **scripted** edit, not a manual one.
- Several files edited within the same second (e.g. `a.py` and `a.py.bak` 700 ms apart)
  indicate a batch operation — a script or an agent applying a multi-file patch.
- Compare against the change's mtime: a backup created immediately before it is the
  strongest single signal of the edit method.

## 3. Trace live agent processes to their origin

For any agent CLI/daemon still running, walk the parent chain to find its terminal and
origin host:

```bash
pid=<agent-pid>
for i in 1 2 3 4 5 6; do
  line=$(ps -p $pid -o pid=,ppid=,stat=,cmd= 2>/dev/null | head -1)
  [ -z "$line" ] && break
  echo "$line"
  pid=$(echo "$line" | awk '{print $2}')
  [ "$pid" = "0" ] || [ "$pid" = "1" ] && break
done
```

A terminal device (`pts/N`) in the chain means an interactive session; a chain ending
at `sshd` means a remote login. `who` / `w` show the source IP for that tty.

Caveat that matters: a process can swap its command-line name, pkill pattern, or port
between invocations while the process tree stays intact. **Process identity is the
stable join key, not the name.** Re-verify with the PID before attributing anything.

A process with `PPID 1` and no tty was orphaned/detached — started by something that
has since exited.

## 4. Correlate with authentication records — from BOTH sources

```bash
journalctl -u ssh --since "<start>" --no-pager | grep -A1 'Accepted'
grep 'Accepted' /var/log/auth.log | tail
```

A file-based log may have **stopped receiving entries** while the journal keeps going.
Before trusting an absence, check that the source is still live:
```bash
tail -1 /var/log/auth.log    # is this timestamp recent?
```
A stale log is not evidence of no activity.

Map an accepted key fingerprint to its owner via the authorized_keys comment:
```bash
ssh-keygen -l -f /root/.ssh/authorized_keys | grep '<fingerprint-prefix>'
```

Important limit: transport authentication (a key) proves **which device**, not which
human. Anyone with access to that terminal inherits the auth. State that limit rather
than implying certainty about intent.

## 5. Agent session-log scan (per-agent forensics)

Agent CLIs keep their own transcripts (often JSONL with `functionCall` / tool entries).
Parse them to list write-shaped operations in a window:

```python
import json, glob
MUT = (' >> ', '> /', 'sed -i', 'systemctl restart', 'docker restart', 'rm -rf')
for path in glob.glob('<agent-home>/chats/*.jsonl'):
    for line in open(path):
        try:
            rec = json.loads(line)
        except Exception:
            continue
        for part in (rec.get('message', {}).get('parts') or []):
            call = part.get('functionCall') or {}
            cmd = str(call.get('args', {}).get('command', ''))
            if any(m in cmd for m in MUT):
                print(rec.get('timestamp', '')[:19], path, cmd[:160])
```

Critical: these logs are **derived artifacts**, not independent witnesses. An agent's
memory file recording another agent's published claim is a *restatement*, not
corroboration. Two files agreeing on a claim that originated from a single source are
one witness, not two. Check whether the record cites another agent's analysis.

## 6. Reported-attribution traps

- A peer agent claiming "X doesn't exist" may have been **truncated by a `head -N`** in
  its own probe. Re-run the search without truncation before accepting it.
- A peer's own-execution exculpation ("my exec was read-only") is a claim about its
  intent and scope, not evidence. Verify the artifact path exists on the node in
  question at all — an actor cannot have written a file that lives on another host.
- Distinguish "no mutations" from "no *deletions*": a summary can be true in the safe
  direction while overstating scope. Check for remote writes, config overwrites, and
  service restarts, not just destructive commands.
- A peer's exculpation ("nothing touched the swap", "no session flushed it") is a claim
  about scope, not evidence — and the lane denying the mutation is often the lane that
  performed it. Walk **its own** process tree for the command string (§3) and check its
  authored commits inside the same window (§9) before accepting the acquittal.
- A number that matches no host in the estate (e.g. a swap total that is neither this
  node's `/proc/swaps` size nor a peer's zero) is unresolved, not rounded. Ask for the
  host + command + timestamp of that reading rather than fitting it to a story.

## 7. State mutations that reverted — use the sampling witness series

Attribution above assumes a durable artifact (a file, a commit). A **reversible state
mutation** — `swapoff -a && swapon -a`, a service bounce, a cache flush — leaves the
system looking normal minutes later, so current state is silent and `/proc/swaps`
reports the restored configuration. Do not conclude "nothing happened".

Read the **time series** produced by a sampling witness instead. Any telemetry unit or
OOM-watcher that logs at a fixed interval carries the transient:

```bash
# fixed-interval telemetry unit — one line per tick with the state
journalctl -u <telemetry-unit> --since "<start>" --no-pager \
  | grep -oE '^[A-Z][a-z]{2} [0-9]{2} [0-9:]{8}.*Swap: [0-9]+ MiB'

# independent second witness: the OOM watcher prints capacity + free every interval
journalctl -u earlyoom --since "<start>" --no-pager \
  | grep -oE 'swap free: *[0-9]+ of [0-9]+ MiB'
```

Signatures that prove the action, without any process record:

- **Total capacity changes and returns** — `8191 → 3934 → 8191 MiB`. A swapfile was
  deactivated (capacity drops by exactly its size) and re-added. Two swapfiles means
  the intermediate total is the surviving file only; do not read it as a partial loss.
- **Used collapses to near zero then climbs** — pages were faulted back into RAM.
- **A side effect in the same window** — RAM available drops by roughly the swapped
  volume as pages return. That drop is a *consequence*, and it is evidence.

Two independent samplers agreeing on the same sequence = one finding with two witnesses.
A single sampler is one witness; say so.

## 8. Bind the mutation to a host before attributing it

Attribution failures are frequently **host conflation**, not missing evidence. A peer on
another box reports the same class of action honestly describing *its* machine; a
`no-op / 0.007s` result is the true answer for a host with no swap unit configured and
the false answer for a host with 8 GB of it.

Probe each node explicitly and print identity with the reading:

```bash
for ip in <nodeA> <nodeB>; do
  ssh -o BatchMode=yes -o ConnectTimeout=4 root@$ip \
    'hostname; free -m | tail -2; swapon --show 2>/dev/null; grep -n swap /etc/fstab 2>/dev/null'
done
```

A node with `Swap: 0 0 0`, no `swapon` table and no fstab line **cannot** have flushed
swap — its no-op was correct. That acquits the node; it says nothing about the other.
Record the hostname beside every number you carry into the report.

## 9. Correlate with authored commits in the same window

An agent lane that mutates state usually also authors commits. Cross-check the two
clocks: the lane's process start (`ps -o lstart`) and the commit times of the repos it
touched.

```bash
git -C <repo> log -8 --format='%h | %ad | %an | %s' --date=format:'%m-%d %H:%M'
```

Same author handle across several repos inside the mutation window, minutes apart, is
strong corroboration that the lane identified from the process tree is the actor. The
handle in `%an` is a **label** — pair it with the process identity from §3, never use it
alone.

## Reporting

Give the actor, the time, the mechanism (patch vs shell vs scripted batch), and the
evidence that pins each. If steps 1-5 all come up empty, say which sources you
searched and what would be needed — "searched X, Y, Z during window W; no record" is a
finding. "Cannot determine" without naming the search is not.
