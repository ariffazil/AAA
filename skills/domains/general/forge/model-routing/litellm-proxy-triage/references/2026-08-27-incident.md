# 2026-08-27 Case Study: ContextWindowExceeded Misdiagnosed as Rate-Limit

## User symptom

> "now my vps kena rate limited lagi. Lite LLM issue ? Fix it"

Arif saw `litellm.ContextWindowExceededError` cascading through forge-777
calls, with `Max Input Tokens=131072, Got=138584` repeated across all
models in the agi-333 pool. Refllex diagnosis was "provider rate limit".

## What actually happened

1. **A-FORGE session had bloated to 138k tokens.** Not a model problem, not
   a quota problem — the session itself was carrying 100k+ of accumulated
   context from prior turns.

2. **Termux-orphan litellm was running.** systemd-federation had been TERM'd
   16 minutes prior (`Aug 27 11:14:48 UTC, code=killed, signal=TERM`). A
   bare-bones litellm was started from a Termux shell via
   `set +m; sleep 2 && /usr/bin/python3 /usr/local/bin/litellm ...` —
   this orphans the process outside systemd's supervision. fed-watchdog
   never noticed.

3. **Fallback chain only had 131k-cap models.** The agi-333 pool's fallback
   chain routed overflow into deepseek-v4-pro (131k) and kimi-k2.5/2.6 (131k)
   — all undersized. The chain had no terminal node with 1M ctx.

4. **`/health` reported 158 unhealthy, 0 healthy** — looked like all
   providers down. Actually the orphan litellm had started during a
   IPv6 flap on provider APIs and never recovered its health probes.

5. **Provider APIs were 100% fine when probed directly with IPv4:**
   ```
   MINIMAX_API_KEY         MiniMax-M3          http=200
   DASHSCOPE_API_KEY       qwen3.7-flash       http=200
   QWEN_INDIVIDUAL_API_KEY qwen3.7-max         http=200
   GEMINI_API_KEY          gemini-2.5-flash    http=200
   ZAI_API_KEY             glm-4.7             http=200
   KIMI_API_KEY            kimi-for-coding     http=200
   ```
   Direct curl with `-4` succeeded in <1s. Default curl (IPv6) timed out —
   the VPS had IPv6 flap on provider endpoints at that moment.

## What fixed it (proposed, not yet executed — pending Arif's "go")

1. Kill orphan PID: `kill 1031575 1031069`
2. `systemctl restart litellm-federation litellm-escape`
3. Patch `router_settings.context_window_fallbacks` — put apex-888 (Gemini
   2.5 Pro, 1M ctx, FREE, proven alive) FIRST in all overflow chains.
4. Prune dead 131k-cap entries from agi-333 that duplicate working
   1M-ctx anchors.

## Lessons extracted (now encoded in litellm-proxy-triage SKILL.md)

1. **Error class rarely matches cause.** Context window ≠ rate limit ≠ outage.
   Probe upstream directly with `curl -4` BEFORE restarting anything.
2. **VPS has IPv6 flap on provider APIs.** Always `curl -4` for health probes.
3. **Never start litellm from Termux `bash -c "litellm ..."`.** Orphans the
   process, breaks fed-watchdog, leaves `/health` permanently stale.
4. **Fallback chains must terminate at a 1M-ctx model.** Otherwise overflow
   cascades through every entry and the federation hangs.
5. **158 unhealthy / 0 healthy ≠ providers down.** More often means litellm
   started during an upstream flap and never recovered.

## Scar

> "Probe before restart. Restart only if probe confirms upstream is fine.
    Never create Termux-orphans. Every fallback chain needs a 1M-ctx terminal."
