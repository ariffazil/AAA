# Three FQ-like systems that are NOT the same thing

When a sibling reports "FQ is 0.0" or "flow_state is stale", you are probably
hearing one of three separate signals. Conflating them produces a wasted
debugging cycle.

## The three systems

| System | Path / source | What it measures |
|---|---|---|
| **arifFlow :7073** (live daemon) | `curl http://127.0.0.1:7073/health` | Federation FQ — execute vs verify ratio across the whole federation |
| **AED daemon** (`aed.service`) | `journalctl -u aed.service` | Per-cycle FQ for ONE execution cycle — different formula |
| **flow_state.json** (mirror cache) | `/root/AAA/state/flow_state.json` (canonical) | Cached snapshot of last arifFlow FQ, written by fq-mirror.service every 60s |

## now_brief.py — what it ACTUALLY reads

```python
# /root/HERMES/scripts/zen/now_brief.py
fq_out = subprocess.run("journalctl -u aed.service --since '2 hours ago' ...",
                        shell=True, capture_output=True, text=True, timeout=3).stdout.strip()
```

**`now_brief.py` reads `aed.service` journalctl. It does NOT read `flow_state.json`.**

`grep -rn 'flow_state' /root/HERMES/scripts/zen/` = 0 matches.

If a sibling says "now_brief.py is reading stale flow_state.json", they guessed
wrong. Data flow: aed.service → journal → now_brief.py greps journal.

## Why AED cycle_fq=0.0 is NOT a bug (likely)

AED is `Type=oneshot`. Each cycle computes `cycle_fq` from what it executed in THAT
cycle. If a cycle ran 0 substantive executions, `cycle_fq=0.0` is correct —
it does NOT mean AED is broken.

arifFlow's FQ (1.28) is independent and healthy. Two systems, two formulas.

## Pre-diagnosis probe order

1. `curl -sf http://127.0.0.1:7073/health` — ground truth arifFlow FQ
2. `systemctl status aed.service` — is AED running?
3. `journalctl -u aed.service --since '2 hours ago' --no-pager -q | tail -20` — last AED cycle
4. `ls -la /root/AAA/state/flow_state.json` — is mirror fresh?
5. ONLY if all 4 confirm issue → patch now_brief.py or flow_state path

## Don't-fix-this note
