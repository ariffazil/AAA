# Fake Hash Detection — Output Attestation Pattern

## Context

2026-08-09: Arif sent a PDF with crypto signoff claiming SHA-256 hash `5334a3d6...`. Verification showed the hash was fabricated — never computed.

## Detection pattern

```bash
# 1. Extract claimed hash from document
grep -o 'SHA-256: [a-f0-9]\{64\}' document.pdf  # or extract from text

# 2. Compute real hash
sha256sum document.pdf
# → 2f9ce7004f7a8293c81c70c37636ae1090cc4a594a71660a04bf302c2d3a4c50

# 3. Compare
# Claimed: 5334a3d6c18cafe5c85e340b450451e79e3bb48d7e648e643325f96e671b3bfe
# Actual:  2f9ce7004f7a8293c81c70c37636ae1090cc4a594a71660a04bf302c2d3a4c50
# → FABRICATED
```

## Using the attestation system

```bash
# Compute and record real hash:
python3 /root/HERMES/scripts/output-attest.py document.pdf --label "surat-v3"
# → {"sha256": "2f9ce7...", "ledger_recorded": true, "verbatim": true}

# Verify against claim:
python3 /root/HERMES/scripts/output-verify.py document.pdf "5334a3d6..."
# → {"verdict": "FABRICATED", "claim_match": false}
```

## What "verbatim: true" means

The attestation ledger marks every entry with `verbatim: true`. This means the hash was COMPUTED from the actual file content, not generated as text. A hash without a ledger entry is unverified. A hash with a ledger entry but `verbatim: false` is suspicious.

## Connection to Gödel Loop

This is the same problem as fake 888-APEX judgment:
- Agent generates text that LOOKS like governance
- But never actually calls the governance layer
- The "verification" is self-certification

The fix: separate claim from computation. The hash must be computed by a tool, not generated by the LLM.
