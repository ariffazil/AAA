# Delegated publication — the verifiable mission contract

Use when a piece is going to a live surface and the build is being handed to another coding
agent ("give me the prompt to give Claude Code").

**The deliverable is a file, not a chat message.** Write the brief to a path in the working
directory and hand over the path. The author pastes the file's contents; he does not want to
reassemble a brief from chat scrollback.

Why this shape: an external coding agent given a task *description* will report success without
proving it. Every section below exists to make a false "done" impossible.

---

## Section order (all mandatory)

### 0. Role and preflight — FAIL-CLOSED

State the agent's role, that epistemic honesty governs every claim it writes and custody governs
every file it touches, and that it may not self-seal. Then a command block whose output it must
paste at the top of its report:

```bash
hostname                                   # must be the host holding repo + web server
cd <repo> && git log --oneline -1          # must be the stated HEAD
sha256sum <each input artifact>
```

Give the expected hashes in the brief and instruct STOP on mismatch. This is the highest-value
section: shared working directories get overwritten by sibling agents mid-task, and a stale input
produces a complete, plausible, wrong deliverable.

### 1. Mission

Exact output URLs (with AND without trailing slash), the asset URL, the byline, the surface it
belongs to — and what it explicitly is NOT ("a route-level page, not an article — do not add it
to the article registry").

### 2. Inputs table

Every source file with its SHA256 and a one-line role, plus the precedence rule for conflicts
("where X and Y disagree, X wins").

### 3. File governance — three buckets

| Bucket | Content |
|---|---|
| CANON | Files to edit, each named with the smallest permitted slice ("add route lines only") |
| DERIVED | Generated by the build — never hand-edit, listed by name |
| NEVER-TOUCH | The sibling's uncommitted in-flight files by path, plus web-server and deploy scripts |

Pull NEVER-TOUCH from `git status --short` before writing the brief. Say explicitly: "you WILL
edit `<file>` but only by adding lines — never revert, reformat, or reorder anything already in
it."

### 4. Content law (print → web)

Numbered, binding, not stylistic:

1. Retitle; set byline; drop internal covering phrases.
2. Retarget: any section addressed to one named reader becomes audience-facing. Keep every number
   and consequence; change only the addressee.
3. **Preserve claim grades verbatim.** No upgrades, no softening; caveats ship with numbers.
4. Invent nothing. If a needed figure is absent, omit the sentence and list the gap.
5. Strip print chrome (`@page`, page-break divs, page numbers, fixed page heights).
6. Keep methodology / correction sections that are load-bearing.
7. One short honest method paragraph; internal seat labels appear at most once, never as narrative.
8. Preserve the source register — do not translate a code-switched text into one language.
9. Dark surfaces only. No new palette, no new stylesheet — reuse the sibling page's classes.

### 5. Implementation notes

Point at an existing sibling page as the pattern. Require the title/canonical effect hook and the
**verification marker** (below). State the one structural pitfall that applies — a common one is
flat asset placement: a page's downloadable asset goes beside the route, never inside a directory
named after the route, because a route-named directory can be matched by the static-file handler
and shadow the client-side fallback, breaking the page itself.

### 6. Wiring

Each route / registry / generator edit listed separately with the exact array or entry to add, and
the reminder that generated outputs are DERIVED. If the project has a design or lint gate, require
it be run before and after with the violation counts in the report.

### 7. Build, deploy, verify

State the build command and the deploy method — and what is forbidden (whole-project deploy
scripts that reload the web server). Note when no server-config change is needed at all, and how
to confirm that before touching anything.

Verification output must be printable per check. Core set:

```bash
curl -so /dev/null -w "shell %{http_code}\n" https://<site>/
curl -so /dev/null -w "page %{http_code} %{size_download}B\n" https://<site>/<route>/
BUNDLE=$(curl -s https://<site>/ | grep -oP 'index-[A-Za-z0-9_-]+\.js' | head -1)
curl -s "https://<site>/assets/$BUNDLE" | grep -c "<MARKER>"     # 0 = stale bundle
curl -so /dev/null -w "asset %{http_code} %{content_type}\n" https://<site>/<asset>
curl -s https://<site>/sitemap.xml | grep -c "<slug>"
curl -s https://<site>/llms.txt   | grep -c "<slug>"
```

Add the sentence that makes the gate honest: **"If the marker count is 0 the bundle is stale —
rebuild, redeploy, recheck. Do not report success on the HTTP check alone."** A client-rendered
route returns 200 for any path, so an HTTP check is not evidence the page exists.

### 8. Prohibitions

Flat list: no whole-project deploy, no web-server reload or config edit, no DNS change, no
`rsync --delete`, no `git stash` / branch switch / `rebase` / `reset` / force push, no committing
the sibling's files, no inventing numbers, no upgrading a grade, no hand-editing a DERIVED file to
make a check pass, no writing "verified" without the proving check in the report.

### 9. Commit

Explicit `git add` paths only, plus the audit note: "if a `git add` path does not exist, that is a
signal to check your work, not to add something else." Push only if the branch tracks an origin;
report a failed push, never force.

### 10. Receipt — fixed section order

Facts before summary: preflight output · files created with line counts · files edited with
`git diff --stat` and hunks · gate violations before/after · build exit code · every verification
check with raw output · commit hash and push status · **UNKNOWN list** · rollback recipe.

Close with the register rule: *state transitions, not verdicts* — "wrote the page, bundle
contains the marker, asset serves 200, commit `<sha>`" rather than "done"; and "if a step failed,
say which step and stop there — do not work around a failure by weakening a check."

---

## Delivery

Hand over the file, then lead the message with **the consequence the author must act on** — must
run on the deploy host; hashes are pinned; what was deliberately changed for the reader. Not a
summary of the brief's contents, but of what happens to the contents he already has. If he asks
"so what", the answer is the decision the artifact forces.
